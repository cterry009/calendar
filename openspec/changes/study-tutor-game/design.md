## Context

The user studies from Obsidian notes ("Notas de Fisica"). Each note has numbered sections with 🟢
Sencillo / 🟡 Medio exercises and a folded answer, some true/false callouts, and a closing with 🔴
Difícil (D1, D2...) and ⚫ Muy difícil (M1, M2...) problems with a hint and a solution. The app already
reads the pensums (`notes/pensum.ts`) into study tasks, and the planner follows the rule "the model
proposes, the code decides". The full design, with the decisions below, is in the vault at
`Tutor_diseno.md` (2026-10-20). Phase 1 builds the two pure layers everything else stands on.

Formats checked against the vault on 2026-10-21 (30 notes with exercises):

- Fundamentos (AN1-AN4, 00b, 01a) and Pilar E (E1, E2): exercises under `## N. Title`.
- Pillars A-D and B1, D1: exercises under `## Desarrollo`, with sections as `### N. Title`.
- Exercise markers: `**🟢 Sencillo.**` / `**🟡 Medio.**` at the start of a line, an optional
  `*(tu respuesta aquí)*` line, then `> [!success]- Respuesta`.
- True/false: `> [!question]- Verdadero o falso (...)`, numbered items `N. claim — **Falso:** why`.
- Closings: `## Cierre — 🔴 Difícil` / `## Cierre — ⚫ Muy difícil`; items `**D1.**` or
  `**D1 (title).**` (⚫ uses `M1`, `M2`...), `*(tu intento aquí)*`, `> [!tip]- Pista`,
  `> [!success]- Solución`.

## Goals / Non-Goals

**Goals:**
- A catalog of every exercise in a note, with ids that stay the same across re-parses.
- A deterministic, tested engine: the same attempts in any order give the same game state.
- Parameters in one `GameConfig` with exported defaults, so the game can be recalibrated by replay.

**Non-Goals (phase 1):**
- Prisma, migrations, sync, server, UI, calls to Claude or Gemini, MCP.
- Changing `import-study-notes.mjs` or `planning/study.ts`.
- Calibrating item difficulty from data (b stays b₀ or the generated exercise's own b).

## Decisions

The project-level decisions come from `Tutor_diseno.md`:

- **D1 Where Claude runs:** in the NestJS server, module `tutor/`, launching `claude -p` (uses the
  logged-in Claude Code session, no API key); reachable from the phone over the LAN. *Phase 3.*
- **D2 Who grades:** Claude proposes a grade and justifies it; the user can correct it with one tap.
  The latest grade counts (`supersedes`).
- **D3 Exercises:** the notes' catalog plus exercises generated by Claude: in-between difficulties and
  notes with no exercises yet (01, 02, 03).
- **D4 Delivery:** one OpenSpec change, applied phase by phase, reviewed before each `/opsx:apply`.
- **D5 Principle:** the model grades and proposes; the code decides. Claude never computes θ, XP or
  levels.
- **D6 Game state:** θ, XP and levels are never stored. They are recomputed by replaying the attempt
  history (event sourcing): deterministic, no sync conflicts, recalibrable when parameters change.

Phase 1 decisions (user-confirmed 2026-10-21 where marked):

- **D7 Sections (user-confirmed).** A section is `## N. ...`, or `### N. ...` inside `## Desarrollo`.
  Inside a numbered `##` section, `###` subsections ("### 1.4 ...") don't start a new section. Any
  other `##` heading ends the context, like `pensum.ts`. Without this, pillars A-D would lose all 53 of
  their 🟢/🟡 and keep only the closings.
- **D8 Ids.** `${noteCode}#${section}#${n}`, n = 1, 2... in order of appearance within the section,
  counting 🟢, 🟡 and true/false together; closings use the item's own label:
  `AN1#cierre-rojo#D2`, `AN1#cierre-negro#M1`. The note code is the file name's prefix before the first
  `_`. Editing a note above an exercise can shift its n (same trade-off as `pensum.ts` keys).
- **D9 True/false.** One exercise per callout. The statement is the claims with the verdicts cut off
  (the text from ` — **Verdadero` / ` — **Falso` on); the answer is the full callout body.
- **D10 Statement and answer text.** The statement runs from the marker to the first callout, without
  the `*(tu respuesta aquí)*` / `*(tu intento aquí)*` placeholder; callout bodies lose their leading
  `> `. LaTeX and markdown are kept as written.
- **D11 θ update.** θ ← θ + K(r − p), K = max(Kmin, K0/√(1 + n)), n = attempts already in that
  section; K0 = 0.8, Kmin = 0.15. b is the attempt's own `b`. r ∉ {0, 0.5, 1} throws.
- **D12 Replay order and corrections.** Attempts are deduplicated by id and sorted by
  (occurredAt, id). An attempt that `supersedes` another takes the place of the one it replaces (a
  chain resolves to its last link; if two claim the same attempt, the later wins). A `supersedes`
  pointing at an unknown id is a normal attempt.
- **D13 Sections and bosses.** θ is per `noteCode§section`. Closing sections (`cierre-rojo`,
  `cierre-negro`) also get a θ, but don't count in the note's mean. Cold start: a section's first θ is
  the mean of the note's non-closing sections seen so far, else 0. A boss is unlocked while
  `probability(note mean θ, b₀) ≥ 0.5` (or once beaten); beaten with r = 1. A beaten 🔴 marks the
  note as closed.
- **D14 XP and combo (user-confirmed reset).** XP = 0 if r = 0, else
  clamp(round(10·r·2^(b − θ_before)), 1, 100) × combo × (3 if boss), rounded. Combo = 1 + 0.1 per
  previous consecutive attempt with r ≥ 0.5, max 1.5. It resets on r = 0 or when more than 90 minutes
  pass since the previous attempt (`comboGapMinutes`). Global level: the largest n with
  100·n^1.5 ≤ XP (0 below 100).
- **D15 Section level (user-confirmed).** A ladder on the kinds' b₀: 1 if θ < −1, 2 from −1 (🟢 at
  50%), 3 from 0 (🟡), 4 from +1 (🔴), 5 from +2 (⚫). Thresholds in `GameConfig`.
- **D16 Review.** r = 0 puts the exercise in the queue; r = 1 takes it out; r = 0.5 leaves it where it
  is. Ordered by when it entered.
- **D17 Next exercise.** b* = θ − logit(0.8). Candidates are the section's catalog exercises never
  attempted (a failed one goes through the review queue, not straight back); bosses only if unlocked.
  The nearest to b* wins if |b₀ − b*| < margin (0.75), ties by note order; otherwise
  `{ type: 'generate', targetB: b* }`.

## Risks / Trade-offs

- [Ids shift when a note is edited above an exercise] → attempts keep `noteCode`, `section` and `b`, so
  the engine still works; a rename map can come in phase 2 if it happens.
- [Fixed b₀ per kind is coarse: every 🟡 is b = 0] → generated exercises fill the gaps (D3); item
  calibration from data is possible later because the state is replayed (D6).
- [Combo resets by time, not by block] → phase 2 can key it on `pomodoroSessionId` when attempts have
  one.
- [Strong students are underestimated at first] → with p* = 0.8 a success moves θ up by 0.2·K and a
  failure down by 0.8·K, so climbing is slow: after 60 attempts a θ = 2 student sits near 1.5 and a
  θ = −2 one near −1.85 (mean bias ≈ −0.076; K0/Kmin changes leave it at ≈ −0.065). Accepted for
  phase 1 (user, 2026-10-21); the bias test guards against it getting worse. Possible later fix: a
  diagnostic warm-up at p ≈ 0.5, or separate up/down step sizes.

- **D18 Convergence test (user-approved 2026-10-21).** With 0/1 answers at p ≈ 0.8, 60 attempts carry
  little information: RMSE ≈ 0.35 for any K schedule (20 000 simulations), and |θ̂ − θ| < 0.5 holds for
  ~84.5% of students, so "9 of 10 seeds" would pass for only ~52% of seed choices. The test instead
  uses 100 students with θ_true uniform in [−2, 2] and a fixed seed, and checks: at least 75 within 0.5
  (passes for ~99% of seed sets), pooled success rate 0.8 ± 0.03 (pooled mean 0.7995, sd 0.007 across
  seed sets) and |mean bias| < 0.15 (~98%; 0.1 would pass only ~75%).

## Phase 2: data and sync (proposed 2026-10-21)

The engine needs the attempts on every device: `replay` rebuilds the game from the **whole** history
(D6), so the 30-day window used for `BlockEvent` doesn't fit. Writers: the server's tutor (phase 3)
records Claude's grades; the web UI (phase 4) records the user's corrections. Phase 2 builds the pipe
between them, with nothing writing to it yet in production.

- **D19 Entity.** `ExerciseAttempt` (`exercise_attempts`): `id` (client UUID, primary key), `userId`,
  `exerciseId`, `exerciseSource` (`nota` | `generado`), `noteCode`, `section`, `b` (float), `r` (float:
  0, 0.5 or 1), `hints`, `minutes?`, `gradedBy` (`claude` | `usuario`), `supersedes?`,
  `generatedStatement?` (text), `feedback?` (text), `studyTaskId?`, `pomodoroSessionId?`,
  `occurredAt`, `createdAt`. Enum values are lowercase so the rows match `ExerciseAttemptInput`
  without mapping. Indexes on (userId, occurredAt) and (userId, noteCode).
- **D20 Immutable and idempotent, like `FocusEvent`.** A create on the client id; a retry (or a
  concurrent duplicate hitting P2002) is `skipped`, never an update. A correction is a *new* attempt
  with `supersedes`. `supersedes` isn't checked against existing rows: `replay` already treats an
  unknown target as a plain attempt, and the original can arrive after its correction from another
  device's queue.
- **D21 Pull without texts (user-confirmed).** `GET /sync/pull` returns every attempt of the user,
  oldest first, without `generatedStatement` and `feedback` (~7 000 attempts a year, ~1.5 MB instead of
  ~5 MB). `GET /sync/exercise-attempts?since=` returns full rows (all of them without `since`), for
  showing a past exercise and its feedback.
- **D22 Validation.** The DTO accepts `r` only in {0, 0.5, 1}, `b` in [−6, 6], `hints` ≥ 0,
  `minutes` ≥ 0, ids and codes up to 200 characters, `generatedStatement` up to 20 000 and `feedback`
  up to 10 000. Whether a generated exercise is well formed is the tutor's job (phase 3), not sync's.
- **D23 Shared schema.** `ExerciseAttemptSchema` (Zod) in `packages/shared/src/schemas/`, whose type
  extends `ExerciseAttemptInput` with the optional fields, so a synced record goes straight into
  `replay`.
- **D24 Clients (user-confirmed).** Web: snapshot field `exerciseAttempts?` (defaulted with `?? []`,
  since cached snapshots predate it), offline entity type and conflict label, and
  `logExerciseAttempt` (through the offline-aware batch, like `logFocusEvent`) for phase 4's
  corrections. Mobile: only the snapshot type and the pull field; writing from the phone comes with
  its UI.
- **D25 Study status export.** `scripts/export-study-status.mjs` adds the game per note (θ and level
  per section, XP, global level, bosses, review queue), replayed from the pulled attempts with the
  catalog parsed from the vault, to both `Estado_estudio.md` and `estado_estudio.json`, as
  `Tutor_diseno.md` asks. With no attempts yet it says so.

## Phase 3: the tutor on the server (proposed 2026-10-21)

Checked first (2026-10-21): `claude` 2.1.292 is at `~/.local/bin/claude.exe` and logged in. A real
`claude -p ... --output-format json --json-schema ...` graded AN1#1#1 correctly (r = 0.5, with a sound
justification) and returned `structured_output`. Cost per turn, at list prices, is mostly Claude
Code's own system prompt (`--bare` would drop it but needs an API key): Opus reading the whole note
22 s / $0.59; Sonnet with the exercise in the prompt 10 s / $0.20; Haiku 16 s / $0.10. On a
subscription this is quota, not money.

- **D26 The server imports `@calendar/shared` (user-confirmed).** First time: a
  `"@calendar/shared": "file:../packages/shared"` dependency, built with `npm run build:shared`
  (CI already builds it before the server). Nest compiles to CommonJS and shared is ESM; Node ≥ 22.12
  (here 24) loads it with `require`, checked on 2026-10-21. One engine for server and clients: the
  catalog parser, `replay` and `nextExercise` are not ported. CLAUDE.md's "the server does not import
  @calendar/shared" changes.
- **D27 Model (user's choice: Opus).** `TUTOR_MODEL` (default `opus`), `TUTOR_CLAUDE_BIN` (default
  `claude`), `TUTOR_TIMEOUT_MS` (default 180 000). The vault is `CALENDAR_VAULT`, as for the planner.
- **D28 How Claude runs.** `spawn` with an argument array and no shell, since the user's message is
  in the arguments: `claude -p <turn> --model <m> --output-format json --json-schema <schema>
  --append-system-prompt-file profesor.md --add-dir <vault> --tools Read --allowedTools Read
  --permission-mode dontAsk`, plus `--session-id <uuid>` on a conversation's first turn and
  `--resume <uuid>` after. The working directory is an empty folder of the server's own (not the
  repo, so the repo's CLAUDE.md and settings aren't loaded). With `dontAsk` and only Read allowed,
  reading outside that folder and the vault is refused.
- **D29 Context (user-confirmed: the exercise plus a bounded Read).** Each turn the server puts in the
  prompt: the current study session (from the user's tasks, as `planning/study.ts` sees it), the
  section's θ and level, the current exercise with its reference answer and hint (or, for a
  generated one, its statement and target b), and the note's path with the **line range of the
  section**. `profesor.md` tells Claude to read only that range (Read's offset/limit) when it needs to
  explain. A new shared helper, `noteSections(fileName, markdown)`, returns each section's title and
  line range with the same rules as `parseExercises`.
- **D30 One endpoint, stateless apart from the conversation.** `POST /tutor/turn` takes
  `{ message, noteCode, section, sessionId?, current?, pomodoroSessionId?, studyTaskId? }`, where
  `current` is the exercise on the table (a catalog id, or a generated exercise as returned by an
  earlier turn). The server:
  1. loads the catalog (vault notes parsed with `parseExercises`, cached by file mtime) and replays the
     user's attempts;
  2. if there is no `current`, picks one with `nextExercise`; a `generate` result asks Claude to write
     one at that b in this turn;
  3. runs Claude and validates the reply (D31);
  4. if Claude graded, records the attempt through the sync service (same idempotent create, so other
     devices get `sync:changes`), replays again and picks the next exercise;
  5. answers `{ sessionId, mensaje, accion, current, attempt?, game: { theta, level, xp, xpGained,
     combo, review }, warnings }`.
- **D31 Validating Claude's reply.** The schema allows `accion` ∈ {explicar, proponer_ejercicio,
  pista, calificar}, a `calificacion { exerciseId, r, pistas, justificacion }` and an
  `ejercicioGenerado { enunciado, respuesta, b }`. The code then checks: a grade is for the current
  exercise only, r ∈ {0, 0.5, 1}, hints ≥ 0; a generated exercise has a statement and gets the
  engine's target b (Claude's own b is ignored: D5, the code decides difficulty) and the id
  `<noteCode>#gen-<8 hex>`. Anything else → 502 `tutor_invalid_reply` and nothing is recorded.
- **D32 Conversations.** A conversation is one Claude session (`--session-id`, then `--resume`). The
  server remembers which user owns which session id in memory; an unknown id (e.g. after a server
  restart) starts a new conversation and says so in `warnings`. One turn at a time per user (429 if one
  is running).
- **D33 When Claude isn't there.** Missing binary, timeout, a non-zero exit or `is_error` → 503
  `tutor_unavailable` with the reason; nothing is recorded, and the block keeps working as before (the
  UI in phase 4 shows it).
- **D34 Read-only game endpoint.** `GET /tutor/state?noteCode&section` returns the replayed state of
  that section and the next exercise, without calling Claude: for the UI and for testing.
- **D35 Testable without Claude.** The CLI sits behind a `TutorModel` interface (like `Planner`);
  tests use a fake model on the real test database. One live test runs only with `TUTOR_LIVE=1`.
