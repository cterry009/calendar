  **Bug: `adb reverse` tunnels are per-transport, not per-device.** Switching from USB to a WiFi/Tailscale `adb connect` (or back) silently drops Metro/API reachability on the new transport even though the old transport's tunnels still show as configured -- the app looked "not responding" (stuck on the splash screen) because it genuinely couldn't reach either server, not because of any app bug. No code fix (this is a dev-tooling behavior, not the app's) -- just re-run `adb reverse tcp:8081 tcp:8081` / `tcp:3000 tcp:3000` against whichever transport is currently active before assuming the app itself is broken.

  **Bug: Express's default 100kb JSON body limit rejected real offline-queue flushes.** A `/sync/batch` flush that had accumulated enough queued changes (confirmed on-device: 352kb, well past the 100kb default) got a 413, and because the exact same oversized payload gets retried identically on every reconnect, the device was stuck permanently showing "Mostrando datos guardados" (cached data) with no path back to a synced state short of a code fix. Fixed in `server/src/main.ts` via Nest 11's `app.useBodyParser('json', { limit: '10mb' })` -- confirmed fixed by watching today's steps land in Postgres immediately after the server restarted with the new limit, with no client-side change needed.
